# 项目采访协议

使用本协议补齐无法从项目文件、Git、测试和安全只读检查中获得的信息。先完成可访问材料的读取与初步审计，再开始采访。

## 核心规则

1. 一次只问一个问题。
2. 每轮选择最能减少当前决策不确定性的问题。
3. 不询问能从项目中安全验证的事实。
4. 先简述已知上下文，再提出短而具体的问题。
5. 不把建议伪装成用户决定。
6. 不替用户填补未知答案。
7. 不要求用户一次填写问卷。
8. 未触及安全门的未知项不得阻塞全部规划。

## 证据状态

为每条信息标记且只标记一个当前状态：

- `VERIFIED`：由代码、Git、配置、测试、构建或可复现运行证据验证。
- `USER_CONFIRMED`：用户明确陈述或确认。
- `INFERRED`：有证据支持但尚未验证的推断；同时记录依据。
- `UNKNOWN`：没有足够信息。
- `NEEDS_TEST`：必须通过后续实验、测试或现场验证确认。
- `REJECTED`：用户明确否定；同时记录原因。
- `CONFLICTED`：不同来源冲突；同时列出冲突来源。

用户回答“不知道”时，标记为 `UNKNOWN`；需要实验才能回答时，标记为 `NEEDS_TEST`。不得改写为 `VERIFIED` 或 `USER_CONFIRMED`。

## 选题顺序

按信息价值动态选择问题，不机械照抄顺序。优先澄清：

1. 项目最终希望为谁带来什么可观察的改变。
2. 真正用户、购买者、维护者和受影响者是否不同。
3. 最核心、最高频或最高风险的使用场景。
4. 可验证的成功标准与最终验收条件。
5. 必须完成的范围。
6. 明确不做的内容。
7. 时间、预算、人力、设备、平台和技术约束。
8. 已有代码、数据、文档、环境、硬件和外部依赖。
9. 已否定方案、失败尝试及其原因。
10. 安全、隐私、合规、部署、运维和维护要求。
11. 不可逆或迁移成本极高的决定。
12. 对稳健、平衡/杠杆或突破路线的偏好及风险承受能力。

## 选择“下一个问题”

为候选问题按以下因素进行快速判断：

- 是否会改变目标或成功标准；
- 是否会改变里程碑依赖图；
- 是否会改变关键路径；
- 是否会触发硬件、生产、隐私或不可逆安全门；
- 是否会排除一条战略路线；
- 是否能避免大规模无效实现；
- 是否只能由用户回答。

优先询问影响大、当前未知、只能由用户回答且能立即改变规划的问题。把可以通过低成本实验回答的问题登记为 `NEEDS_TEST`，优先设计验证里程碑，而不是持续追问。

## 提问格式

使用以下结构，每轮只保留一个问号：

```text
目前已确认：[与问题直接相关的简短事实]。
为了决定[将受影响的规划选择]，请确认：[单一问题]？
```

必要时给出不超过三个互斥选项，并允许用户用自己的话回答。不得把推荐选项视为默认确认。

## 处理冲突与否定

- 用户陈述与代码或测试冲突时，将条目标记为 `CONFLICTED`，说明两个来源，不擅自裁决。
- 用户否定方案时，将方案及原因标记为 `REJECTED`，避免后续重复建议。
- 用户修正先前回答时，保留变更记录，并以最新明确确认更新当前状态。
- 涉及凭据、个人数据或商业秘密时，只询问约束和数据分类，不要求用户在聊天中粘贴秘密。

## 安全门问题

以下未知项未解决前，不得规划其后的危险执行步骤为 `READY`：

- 真实硬件供电、烧录、执行器动作或可能损坏设备；
- 生产环境写入、数据迁移、删除或不可逆变更；
- 敏感数据访问、导出或外部传输；
- 缺少授权、备份、回滚、隔离或停止机制；
- 法规、许可或责任边界不清。

将对应里程碑设为 `WAITING` 或 `BLOCKED`，明确所需人工批准或验证证据。

## 停止采访

满足以下全部条件后停止采访并形成第一版规划：

- 项目目标足够明确；
- 成功标准可验证；
- 关键约束已识别；
- 高风险未知项已显式登记；
- 能形成包含 3 至 12 个里程碑的第一版依赖图。

停止采访不代表所有问题都已回答。将剩余问题写入项目胶囊和 `thread-plan.json` 的 `unresolved_questions`，并把可实验验证的问题分配给明确里程碑。
