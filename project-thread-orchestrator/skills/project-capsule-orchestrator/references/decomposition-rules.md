# 里程碑线程拆分规则

将项目拆分为 3 至 12 个有向无环的顶层里程碑线程。线程是可独立验收的边界，不是普通待办项。

## 1. 先建立依赖，再命名线程

按以下顺序识别工作：

1. 项目信息、事实基线和安全边界；
2. 软件、构建、测试、回滚和可观测性基线；
3. 风险最高的未知假设及其最小验证实验；
4. 核心架构、数据模型和接口；
5. 可独立验收的功能垂直切片；
6. 集成与系统测试；
7. 部署、文档和交付；
8. 长期优化或突破性实验。

先画依赖边，再计算关键路径和并行组。不得为了凑并行而删除真实依赖。

## 2. 线程边界

每个线程必须：

- 只有一个主要目标；
- 产生明确输出物；
- 具备可观察、可执行的验收标准；
- 有明确允许与禁止修改范围；
- 能在完成后停止，不自动进入下一线程；
- 小到可单独验证，大到能交付一个有意义的里程碑。

禁止创建：

- “完成整个项目”或“处理所有剩余问题”；
- 同时承担无关架构、产品和交付目标；
- 没有输出物或验收标准的研究线程；
- 依赖自身或形成循环的线程；
- 仅以工时、人数或聊天长度划分的线程。

## 3. 命名与数量

- 使用 `M0 简洁任务名称`、`M1 简洁任务名称` 的完整 `name` 格式；名称前缀必须等于该线程的 `milestone_id`。
- 使用匹配 `M0`、`M1`、`M2` 等格式的唯一 `milestone_id`；推荐从 `M0` 连续编号。
- 保持名称具体、可区分，并体现结果而非活动。
- 总数少于 3 时，确认是否其实只是普通小任务；总数超过 12 时，先合并同一阶段内高度耦合的工作或建立后续项目。

## 4. 必填线程字段

每个 milestone 必须包含：

- `milestone_id`
- `name`
- `goal`
- `rationale`
- `dependencies`
- `initial_status`
- `critical_path`
- `parallel_group`
- `execution_mode`
- `project_cwd`
- `required_files`
- `allowed_paths`
- `forbidden_paths`
- `outputs`
- `acceptance_criteria`
- `validation_commands`
- `risks`
- `stop_conditions`
- `capsule_updates`
- `initial_prompt`

使用项目 schema 规定的具体数据类型。路径应相对项目根目录表达，`project_cwd` 除外。

## 5. 状态

`initial_status` 及后续状态只允许：

- `DRAFT`：结构仍在规划或尚未完成预览；
- `READY`：依赖、安全门和执行条件均满足，但尚未执行；
- `WAITING`：等待前置依赖、用户放行或约定事件；
- `BLOCKED`：存在需要处理的明确阻塞；
- `ACTIVE`：用户已明确放行且正在实施；
- `REVIEW`：输出已产生，等待验收；
- `DONE`：验收标准已验证；
- `ARCHIVED`：线程已归档，不再活动。

规划和插件初始化阶段不得使用 `ACTIVE`、`REVIEW` 或 `DONE` 伪装进度。新线程第一次运行只按初始化协议报告：

- `READY`：所有前置依赖已验证完成且没有安全门；
- `WAITING`：仍依赖其他里程碑、用户放行或存在明确阻塞，并同时报告阻塞原因。

`BLOCKED` 仍是注册表和后续生命周期允许的状态，但初始化线程不得自行越过
`READY`/`WAITING` 二选一边界。插件创建前可保留 `DRAFT`。所有状态都必须由证据支持。

## 6. 执行模式

只允许：

- `readonly`：调查、审计或设计；不得修改业务文件；
- `local`：在当前项目工作区内修改允许路径；
- `worktree`：在独立 Git worktree 中隔离修改；
- `hardware-gated`：涉及真实硬件，必须通过人工阶段门；
- `production-gated`：涉及生产或敏感数据，必须通过人工阶段门。

执行模式不能替代安全批准。`hardware-gated` 和 `production-gated` 在批准与防护证据缺失时必须为 `WAITING` 或 `BLOCKED`。

## 7. 依赖与关键路径

- `dependencies` 只引用计划中真实存在的 `milestone_id`。
- 依赖图必须是 DAG。
- 若 B 的验收依赖 A 的输出或证据，则添加 `A -> B`。
- 若两个线程修改相同核心文件、共享不可并发资源或会互相改变验收基线，则将其串行。
- 将决定最早交付时间或安全放行顺序的节点标记 `critical_path: true`。
- 顶层 `critical_path` 必须按依赖顺序列出有效 milestone ID，并与节点标记一致。
- 关键路径不是“最重要线程列表”；它必须尊重依赖。

在无工期估算时，可用“通向最终验收且不可并行绕过的最长依赖链”作为第一版关键路径，并将其标记为推断。

## 8. 并行规则

仅在以下条件全部满足时允许并行：

- 所有共同前置依赖均已满足；
- `allowed_paths` 不重叠，或重叠部分只读；
- 不修改同一核心接口、迁移、锁文件或配置基线；
- 不竞争唯一硬件、环境或生产窗口；
- 一个线程的验证不会使另一个线程的基线失效；
- 合并顺序不影响结果。

使用 `parallel_group` 表示候选并行批次；没有安全并行组时使用 schema 允许的空值。相同 `parallel_group` 不自动授权并行，仍需在执行前复核。

## 9. 高风险未知项

- 将高风险假设拆成最小、可逆、低成本实验。
- 优先验证会推翻架构或产品路线的假设。
- 先建立测试、备份、回滚、监控和急停能力，再安排危险重构或现场操作。
- 为硬件、生产、隐私和不可逆决策设置人工阶段门。
- 将失败判据写入 `stop_conditions`，不要只写成功判据。

顶层 `safety_gates` 使用对象数组。每项只包含：

- `gate_id`：唯一且以 `G` 开头；
- `description`：风险或审批边界；
- `applies_to`：一个或多个真实 milestone ID；
- `approval_required`：布尔值；
- `release_condition`：可验证的解除条件；
- `status`：`OPEN`、`SATISFIED` 或 `WAIVED`。

机器可读计划的 `selected_strategy` 只使用 `ROBUST`、`LEVERAGE`、`BREAKTHROUGH`。

## 10. 路径边界

- `required_files` 列出线程开始前必须读取的胶囊、任务卡和相关技术文件。
- `allowed_paths` 采用最小充分范围。
- `forbidden_paths` 明确业务无关目录、秘密、生产配置、硬件控制和其他线程所有范围。
- 父目录过宽时进一步收紧；不得使用磁盘根目录。
- 两个写线程的 `allowed_paths` 重叠时，默认串行，除非能证明修改对象互不干扰。

## 11. 输出与验收

- `outputs` 描述可定位的文件、接口、报告、测试或决策记录。
- `acceptance_criteria` 使用可观察条件，避免“完善”“优化”“基本可用”。
- `validation_commands` 只列可安全运行且能证明验收条件的命令；未知或危险命令写入阶段门，不自动运行。
- `risks` 使用对象数组；每项只包含 `description`、`severity`、`likelihood`、`mitigation`。严重程度和可能性只使用 `HIGH`、`MEDIUM`、`LOW`。
- `capsule_updates` 明确完成后更新哪些长期记忆文件。

## 12. 拆分复核

生成计划前逐项检查：

- 数量在 3 至 12；
- ID 唯一；
- 依赖目标存在；
- 图无环；
- 每个线程只有一个主要目标；
- 所有线程可独立验收；
- 相同核心文件写入已串行；
- 关键路径连续且真实；
- 并行组满足文件与资源隔离；
- 高风险线程存在安全门和停止条件；
- 没有线程在初始化时自动实施；
- 没有无边界“完成整个项目”线程。
